## Sessões simultâneas

- 4 usuários distintos (signup → aprovação admin automática) × 3 chats cada,
  todos com runs ativas concorrentes, 3 rounds por chat = **36 runs, 36
  completadas, 0 falhas** em 9.6s.
- `run_e2e` p50 = 304 ms, p95 = 8.9 s: a cauda vem da serialização do
  dispatcher (`ChatRunDispatcher.MaxConcurrent = 4` execuções globais +
  1 run por chat), não de erro — runs enfileiradas simplesmente esperam.

## Sub-agentes concorrentes (`delegate_task wait=false`)

- 6 chats-pais por onda × 2 delegates/turno × 2 ondas = **24 runs filhas
  spawnadas e 24 completadas** (parentRunId correto, chats-filhos isolados).
- Gate de aprovação: cada call emitiu `approval_asked` no SSE e foi aprovada
  via `POST /{chat}/runs/{run}/approvals/{call}` (remember=true) — 6
  aprovações, latência p50 ~2 ms.
- Fan-out total das 2 ondas: 1.57 s; filhos executados em paralelo dentro do
  teto de 4 workers do dispatcher.

## Passe real (OmniRoute)

- 4 runs concorrentes com modelo real via provider openai-compatible:
  todas completadas, run_e2e ~7.0 s (latência do LLM real).
- `delegate_task` com modelo real: o modelo emitiu `builtin_delegate_task`
  (forma `builtin_*` casada por `ToolExecutor.FindTool`), gate aprovado,
  run filha spawnada e completada com o mesmo provider — caminho de
  sub-agente validado fim-a-fim com LLM real.

## Observações / gargalos

1. **Write contention SQLite**: sob ~250 req/s com ~40% de writes
   (enqueue/chat_create), p95 do `enqueue` foi a ~519 ms e p99 ~939 ms
   (vs ~34 ms p50). Erros: zero — degrada latência, não quebra.
2. **`GET /api/models`** é o endpoint mais caro (fan-out aos providers
   por request): p99 ~2.3 s sob carga. Candidato a cache curto.
3. **Fila do dispatcher** saturou durante o cenário rps (pending ≥ 50 —
   limite do `ListAllRuns`, profundidade real maior) e drenou por completo
   logo após o fim do burst (~s a drenar). Nenhuma run perdida.
4. **SSE attach** sob alta concorrência de fila: p95 ~8.6 s porque o attach
   abre o stream e aguarda a run sair da fila — comportamento correto de
   backpressure (o cliente recebe backlog + eventos vivos).
5. **Rate limit**: default desligado (`ratelimit.enabled=false`); login tem
   lockout próprio (5 falhas → 5 min) — o harness deixa de martelar signin
   após o provisioning.
